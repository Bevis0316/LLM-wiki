## 二、步驟四：流程反思（作業繳交必填）

### 1. 哪一個節點最常出錯？
實際跑過完整流程後，最容易出錯的節點有兩個：
- **草稿生成節點（Phase B - B3）**：AI 在把技術型 Wiki 濃縮成新手簡報時，最容易犯兩種錯——一是順手沿用專有名詞（如 SIMD、SfM、NDC）卻忘記用白話解釋；二是在做跨篇比較表時「過度簡化」，把不同論文的前提混為一談（例如把「解析式 SDF 可即時渲染」與「神經 SDF 訓練很慢」混在一起講）。
- **多格式來源入庫節點（Phase A - A0）**：當來源混雜 Markdown 網頁剪藏與 23 頁 PDF 投影片時，如果沒有先統一轉成帶頁碼的純文字萃取檔，後續追溯來源與自動化腳本檢查都會斷裂。

### 2. 發現問題後，你把檢查往前移到了哪一個步驟？
- **把「忠實度與新手可讀性檢查」往前移到 Markdown 草稿階段（關卡 3）**：原本容易等到 HTML 簡報做好、打開瀏覽器看才發現文字太專業或與 Wiki 有落差，那時回頭改 HTML 成本很高。把檢查前移到 `03_探索/簡報草稿.md` 後，只需改純文字就能修掉術語與泛化問題。
- **把「來源追溯與斷鏈檢查」透過 `scripts/check_wiki.py` 往前移到每篇匯入結束（關卡 1）**：不等全部做完才對照，而是每匯入完成就用程式驗證 `sources:` 與 `[[雙向連結]]`。

### 3. 你有沒有因此修改 workflow / graph？為什麼？
**有，做了兩項具體修改**（已反映在 `AGENTS.md` 與 `03_探索/流程圖_Loop與Graph.md` v2）：
1. **在 Phase A 最前端新增「Step 0：非純文字預處理分支」**：判斷來源是否為 PDF，若是則先「保留唯讀原檔＋建立帶頁碼的同名 `.md` 萃取檔」，確保所有來源進入同一條純文字管線。
2. **將 Phase B 的 HTML 簡報拆成「固定渲染引擎（`index.html`）＋純資料檔（`slides-data.js`）」**：這樣關卡 3 專心審核文字、關卡 4 專心用腳本審核 JSON 對應與版面，大幅降低每次修正內容時改壞前端互動程式的風險。
